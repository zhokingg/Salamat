## 1. Три наблюдения — что оказалось на самом деле

### 1.1 Ссылка ведёт на localhost:3000

**Адрес редиректа в коде не задан нигде.** Поиск по `lib/` даёт ноль
совпадений на `redirectTo`, `emailRedirectTo`, `localhost`.
`AuthService.linkEmail` ([auth_service.dart:102](../lib/services/auth_service.dart#L102))
вызывает `updateUser(UserAttributes(email:, password:))` без параметра
редиректа, значит GoTrue подставляет Site URL проекта. Правка в дашборде —
правильное место, менять в коде нечего.

**Но одного Site URL не хватит.** Даже с рабочим адресом ссылка не сможет
вернуться в приложение:

| | состояние |
|---|---|
| URL-схема в `ios/Runner/Info.plist` | `CFBundleURLTypes` отсутствует |
| пакет для диплинков (`app_links`, `uni_links`) | нет в `pubspec.yaml` |
| подписка на `onAuthStateChange` | объявлена в [supabase_service.dart:63](../lib/services/supabase_service.dart#L63), **не используется никем** |
| flow | `AuthFlowType.pkce` ([supabase_service.dart:31](../lib/services/supabase_service.dart#L31)) — код обмена должен вернуться в тот же клиент |

Само подтверждение при этом происходит на сервере: браузер дёргает
`/auth/v1/verify`, почта подтверждается, и только потом идёт редирект на
битый адрес. То есть человек, открывший ссылку, аккаунт скорее всего
подтвердил — он просто увидел ошибку в браузере и не понял этого.

### 1.2 Пустой профиль после входа — воспроизведено, причина найдена

Причина **не** в uid и **не** в базе. Данные на месте и читаются; приложение
их не перечитывает.

Прогон `integration_test/auth_diag_test.dart`, вывод дословно:

```
A uid = 0645335c-6fc2-4817-afae-43f459f1469b
[A] userProvider     = name="Аида" norm=2100 age=31 height=168.0 weight=77.1
[A] profileProvider  = 0645335c-6fc2-4817-afae-43f459f1469b

--- swapping session to B (129882e0-647b-49ca-b258-470c866da672) ---
setSession -> uid 129882e0-647b-49ca-b258-470c866da672
[B] session uid      = 129882e0-647b-49ca-b258-470c866da672
[B] userProvider     = name="" norm=null age=null height=null weight=null
[B] profileProvider  = 0645335c-6fc2-4817-afae-43f459f1469b   ← аккаунт A
[B] meals in diary   = 4
[B] weight logs      = 0
[B] water ml         = 750                                    ← вода аккаунта A

B profiles row (live) = {id: 129882e0-647b-49ca-b258-470c866da672,
  name: Бахыт, gender: female, goal: lose, age: 31, height: 168,
  weight: 77.1, calorie_norm: 2340, is_pro: false, ...}
B meals in db = 4: Яблоко, Куриная грудка на гриле, Плов, Овсянка на молоке
```

Сессия сменилась правильно. Строка профиля аккаунта B в базе полная.
`profileProvider` при этом **всё ещё держит id аккаунта A** — то есть за всё
время он не перезапрашивался ни разу.

По четырём вопросам из задачи:

| вопрос | ответ | чем подтверждено |
|---|---|---|
| uid сессии совпадает с uid профиля в базе? | **да**, совпадает | `session uid` = `B profiles row.id` = `129882e0…` |
| привязка почты создаёт новую запись в `auth.users`? | **нет.** `PUT /auth/v1/user` — обновление текущего пользователя, создать вторую запись он не может | живой `PUT` вернул тот же id `c9d8cb9f…`, что и до вызова |
| где флаг «онбординг пройден»? | **локально**, `SharedPreferences`, ключ `onboarding_completed` ([onboarding_flag.dart:14](../lib/services/onboarding_flag.dart#L14)). Вход его не выставляет; выход — стирает ([profile_screen.dart:388](../lib/screens/profile/profile_screen.dart#L388)) | — |
| перечитывается ли профиль после смены сессии? | **нет** | `profileProvider` остался с id аккаунта A |

**Механизм.** `SignInScreen._submit`
([auth_forms.dart:387-392](../lib/screens/auth/auth_forms.dart#L387)) после
успешного входа сбрасывает три провайдера:

```dart
ref.invalidate(userProvider);        // → пустой UserState: name "", norm null
ref.invalidate(mealsProvider);       // → перечитает дневник нового аккаунта
ref.invalidate(subscriptionProvider);
```

`profileProvider` в этот список не попал. А он —
[bootstrap_provider.dart:65-73](../lib/providers/bootstrap_provider.dart#L65) —
единственное место во всём приложении, которое вызывает
`hydrateFromProfile`. Он `FutureProvider`, зависит только от
`bootstrapProvider`, который давно завершился, и потому не перезапускается
никогда. Итог: `userProvider` обнулили, а заполнить его больше нечем.

Дальше это выходит на экран:
* `dashboardGuestName` / `profileGuest` → «друг» / «Гость»;
* `user.calorieNorm ?? 2000` ([dashboard_screen.dart:79](../lib/screens/dashboard/dashboard_screen.dart#L79)) → норма 2000 вместо 2340;
* возраст, рост, вес, цель — прочерки.

`docs/auth-shots/auth_2_B_dashboard.png` — «Привет!» без имени, **825 ккал
осталось** (это 2000 − 1175, а по норме аккаунта было бы 1165),
вода **0,75 л** от предыдущего аккаунта, вес — «Запиши первое взвешивание».
`docs/auth-shots/auth_3_B_profile.png` — «Гость» и пять прочерков.

**Данные при этом достижимы.** В том же прогоне, ничего не меняя в коде,
из теста перечитаны три провайдера, которые вход не трогает:

```
[B-after-reread] weight logs      = 4        (было 0)
[B-after-reread] water ml         = 1250     (было 750)
```
и через пару секунд, когда догрузился профиль — `auth_6_B_profile_after_reread.png`:
**Бахыт · 31 год · 168 см · 77 кг · Похудеть · 2340 ккал.** Всё правильное.
Единственное, чего не хватает на пути входа, — это перечитывание.

Отсюда же следствие: **после перезапуска приложения профиль чинится сам**,
потому что `profileProvider` в новом процессе стартует с нуля. То, что видел
ты, — состояние ровно до первого перезапуска.

Почему «ноль записей»: дневник читает только сегодняшний день
([supabase_service.dart:183-188](../lib/services/supabase_service.dart#L183),
`eaten_at >= начало суток`). Если в аккаунте сегодня ещё не ели, дневник
пустой законно. В прогоне блюда были за сегодня и подтянулись — 4 из 4.

Почему «сразу открывается онбординг»: выход стирает
`onboarding_completed`, вход его обратно не ставит. Пока человек не
перезапустит приложение (splash пере-прочитает профиль и вернёт флаг), любой
уход на `/splash` отправит его на первый шаг онбординга.

### 1.3 Экрана регистрации нет — подтверждаю

`signUp` не вызывается нигде в `lib/`. Единственный способ завести почту —
`showAttachEmailSheet` изнутри уже существующей анонимной сессии.
На проекте регистрация при этом разрешена: `GET /auth/v1/settings` →
`"disable_signup": false`.

## 3. Баги по серьёзности

### Теряются данные

1. **После выхода приложение остаётся без сессии до перезапуска.** `upsertUser` возвращает `null`, записи не сохраняются, ошибки не показывается. — `supabase_service.dart:16,42`
2. **Вода и корзина продуктов лежат в общих ключах prefs** и переезжают в следующий аккаунт. — `water_provider.dart:67`, `pantry_provider.dart:13`
3. **Целевой вес, уровень активности и опыт не пишутся в `profiles` и не читаются оттуда** (`upsertUser` их не отправляет, `hydrateFromProfile` не разбирает). Восстановить аккаунт — потерять цель. — `supabase_service.dart:80-89`, `user_provider.dart:263-273`
4. **`delete-account` не задеплоена** — удалить аккаунт нельзя, требование сторов не выполнено. — живой `404`

### Ломается вход

5. **Профиль не перечитывается после смены сессии** — главный баг наблюдения №2. — `auth_forms.dart:387-392`, `bootstrap_provider.dart:65`
6. **Вес и вода не инвалидируются** — на экране остаются данные предыдущего аккаунта. — там же
7. **Восстановления пароля нет вообще.** Забыл пароль — аккаунт потерян.
8. **Экран входа достижим только с приветствия** — уже онбординувшийся человек войти не может.
9. **Регистрации нет** — наблюдение №3.
10. **`email_not_confirmed` показывается как «проверь связь»** — самый частый случай после битой ссылки. — `auth_service.dart:159-188`

## 4. Что проверить не удалось и почему

**Всё, что требует живого письма.** На проекте включено подтверждение адреса
(`GET /auth/v1/settings` → `"mailer_autoconfirm": false`) и работает встроенный
SMTP Supabase с квотой в пару писем в час. Любая отправка возвращает
`429 over_email_send_rate_limit` — и `PUT /auth/v1/user` (привязка), и
`POST /auth/v1/signup` (регистрация). Причём **пользователь при этом не
создаётся**: проверено — signup вернул 429, последующий вход тем же паролем дал
`invalid_credentials`.

Отсюда непроверенными остались: доставка письма, сам переход по ссылке, вход с
подтверждённым адресом, вход с неподтверждённым адресом, повторная привязка,
привязка занятого адреса, мягкое предупреждение при выходе из аккаунта с
почтой, сохранность подписки при привязке. Все они откроются сразу, как только
в дашборде будет настроен собственный SMTP.

**Живая подписка.** Продукты в App Store Connect не доведены до состояния, в
котором SDK отдаёт офферинги, поэтому «что видит платящий» и «вход в аккаунт с
подпиской» проверялись только по коду.

**Поведение без сети.** Ветки `offline` разобраны по коду; физически сеть у
симулятора не отключалась.

**Прямое чтение `auth.users`.** Служебного ключа у меня нет и в `.env` я не
лезу, поэтому uid читались из JWT (`sub`) и из `GET /auth/v1/user`, а строки —
через REST под сессией самого пользователя. Для вопроса «тот ли uid» этого
достаточно: сравнивались id сессии и id строки в `profiles`.

**Твой аккаунт.** Его почту и пароль я не знаю, так что реальный
`signInWithPassword` в приложении не выполнялся. Смена сессии в прогоне сделана
через `setSession(refresh_token)` — для клиента это то же самое событие
(сессия заменяется, `auth.uid()` меняется), а весь баг находится в том, что
приложение делает **после** этого момента.

## 6. Что сделано и чем проверено

### 6.1 Перечитывание состояния при смене сессии

Список `ref.invalidate` из `SignInScreen._submit` убран целиком. Вместо него —
`lib/providers/session_provider.dart`:

```dart
final authEventProvider = StreamProvider<AuthState>((ref) async* {
  await ref.watch(bootstrapProvider.future);
  yield* SupabaseService.authChanges;      // тот самый поток, который никто не слушал
});

final currentUidProvider = Provider<String?>((ref) {
  ref.watch(authEventProvider);
  return SupabaseService.currentUser?.id;
});

Future<String?> awaitSession(Ref ref) async {
  await ref.watch(bootstrapProvider.future);
  return ref.watch(currentUidProvider);
}
```

Каждый провайдер с данными одного аккаунта теперь начинается с
`await awaitSession(ref)` вместо `await ref.watch(bootstrapProvider.future)` —
это один и тот же вызов по смыслу (дождаться старта), только он заодно
привязывает провайдер к сессии. Забыть строку нельзя: без неё провайдер вообще
не дождётся старта. `userProvider`, `subscriptionProvider` и `pantryProvider`
(они синхронные) делают `ref.watch(currentUidProvider)` в `build`.

`profileProvider` дополнительно понадобилось **удержать живым**: его никто не
слушает после сплэша, а невыслушанный провайдер Riverpod не хранит — его
пересборка по смене uid никого не будила. Один `ref.watch(sessionBindingProvider)`
в `SalamatApp` держит его на весь запуск и заодно синхронизирует RevenueCat.
Значение всегда `null`, так что сам `SalamatApp` от этого не перерисовывается.

### 6.6 Восстановление пароля

`AuthService.sendPasswordReset` (`resetPasswordForEmail`) + экран
`/forgot-password`, ссылка «Забыли пароль?» на экране входа. Экран
`/new-password` меняет пароль на текущей сессии — туда ведут два пути: ссылка
восстановления и строка «Сменить пароль» в настройках.

Ответ одинаковый независимо от того, есть ли аккаунт на этом адресе: иначе
экран превращается в способ узнать, кто пользуется приложением.

**Не работает до двух правок вне кода** — см. §7.

### 6.7 RevenueCat

`PurchasesService.switchUser(uid)` зовётся из `sessionBindingProvider`, то есть
на каждом изменении `currentUidProvider` — вход, выход, привязка почты
(`updateUser` тоже поднимает auth-событие). Из живого лога:

```
[PurchasesService] logIn 1843040b… -> e8f0a351…      (вход)
[PurchasesService] logIn e8f0a351… -> fe3f9872…      (выход, на свежий анонимный)
[B] RevenueCat id = e8f0a351-1774-4a1f-95ca-5d583b029cac
```

`app_user_id` равен Supabase uid в каждый момент — это то, по чему
`revenuecat-webhook` находит профиль. На выходе зовётся `logIn` на новый
анонимный uid, а не `logOut`: анонимная сессия Supabase уже создана, и держать
эти два id одинаковыми важнее, чем формально «разлогиниться».

### 6.8 Ключи prefs и целевой вес

`userScopedKey('water_local_today')` и `userScopedKey('pantry_items')` —
теперь с суффиксом uid. Корзина продуктов один раз переезжает со старого
общего ключа на ключ текущего аккаунта (`adoptLegacyKey`), иначе для того, кто
уже пользуется приложением, это выглядело бы как потеря списка. В прогоне
видно: у аккаунта A корзина `[Курица, Рис]`, после смены на B — `[]`.

Целевой вес, уровень активности и опыт теперь пишутся в `profiles` и читаются
обратно. Колонок для них нет — **миграция `0010_profile_goal_fields.sql`
написана и НЕ применена**, применяешь ты. Пока её нет, `upsertUser` ловит
`PGRST204` и повторяет запись без этих трёх полей, так что ничего не ломается:

```

```

Разобран раньше веток `invalid` / `credentials` — они ловили его первыми и

## 7. Что осталось за пределами кода

**Почта по-прежнему не ходит.** Встроенный SMTP, квота порядка двух писем в
час. За время работы: `signup` → `429`, `recover` → занял слот, шесть попыток
подряд с интервалом 70 с → `429` каждая. Поэтому не проверены живьём:
доставка письма регистрации, письмо восстановления, вход с неподтверждённым
адресом, привязка занятого адреса. Всё это откроется после настройки
собственного SMTP в дашборде.

**Ссылка из письма — сторона приложения готова.** Схема `kg.salamat.app`
зарегистрирована в `ios/Runner/Info.plist`, адрес возврата
`kg.salamat.app://login-callback` передаётся в `signUp`, `updateUser` и
`resetPasswordForEmail`, а событие `passwordRecovery` уводит на
`/new-password`. Проверено на симуляторе: `xcrun simctl openurl` с этой схемой
дал в логе `handle deeplink uri`, дальше — ожидаемое `Code verifier could not
be found in local storage` (код был выдуманный, этот телефон его не запрашивал).

**Осталось одно, в дашборде:** добавить `kg.salamat.app://login-callback` в
Redirect URLs проекта (Authentication → URL Configuration). Пока адреса нет в
списке, GoTrue молча подставит Site URL — это и есть тот самый
`localhost:3000`.

**Миграция `0010` не применена** — целевой вес до этого не сохраняется
(приложение при этом работает, см. 6.8).

**Из «не тронутого» закрыто:** таймаут 10 с у всех вызовов авторизации;
`logFood` больше не глотает ошибку — запись откатывается и человек видит
сообщение; `aida@example..com` отсекается клиентской проверкой. Требования к
составу пароля сознательно не добавлены — восьми символов достаточно.

## 9. Что вылезло по ходу

**Redirect URL всё ещё не прописан.** Во всех письмах —
`redirect_to=https://salamat.fit/**`, хотя приложение передаёт
`kg.salamat.app://login-callback`. GoTrue подставляет запасной адрес, когда
запрошенного нет в списке разрешённых. Плюс сам запасной адрес — с
буквальными `**`: `https://salamat.fit/**?code=…` не откроет ни одну страницу.

Два поля в **Authentication → URL Configuration**:
* **Redirect URLs** — добавить `kg.salamat.app://login-callback`
  (шаблон вида `https://salamat.fit/**` там уместен, но он шаблон, а не адрес);
* **Site URL** — поставить настоящий адрес, `https://salamat.fit`. Сейчас там,
  судя по подстановке, лежит строка с `**`.

Пока это не сделано, письма приходят и подтверждают аккаунт, но ссылка ведёт в
никуда, и человеку приходится возвращаться в приложение руками.

**Строка «Аккаунт» в настройках не обновлялась сразу после привязки** —
исправлено, см. §10.

## 10. Строка «Аккаунт» после привязки

**Что было.** На `live_5_attached.png` лист говорит «Проверь почту… ушло на
salamat-b-f32e71@…», а строка под ним — всё ещё «Почта не привязана».

**Почему.** Экран смотрел на `currentUidProvider`, а привязка uid не меняет —
в этом весь её смысл. `updateUser` честно шлёт `AuthChangeEvent.userUpdated` и
обновляет сохранённого пользователя (`gotrue_client.dart:782-783`), но
провайдер сводил это событие к прежней строке, и `Provider` никого не будил.

**Что стало.** Появился `SessionIdentity` — uid, почта, ожидающая
подтверждения почта и признак анонимности, со значимым равенством, — и
`currentUserProvider`, который его отдаёт. `currentUidProvider` теперь просто
`ref.watch(currentUserProvider).uid`, то есть намеренно уже: привязка почты не
повод перечитывать дневник, это дневник того же аккаунта. Экран настроек
смотрит на identity целиком.

Равенство по значению здесь и есть защита: обновление токена раз в час даёт
такую же запись, и никто не просыпается.

## 11. Ссылки из писем: email_change и всё остальное

### Что было

Ссылка из письма о смене почты открывала приложение и упиралась в
`Route not found: kg.salamat.app://login-callback/#access_token=…` — голый
текст исключения, с токенами человека внутри.

### Почему для этого письма приходит implicit, а не PKCE

Не настройка и не сервер — пробел в `gotrue-dart`. Код challenge генерируется
ровно в трёх местах: `signUp` (`gotrue_client.dart:221`), `signInWithOtp`
(`:471`) и `resetPasswordForEmail` (`:618`). А `updateUser` — тот вызов,
которым привязывается почта — собирает запрос из `headers`, `body`, `jwt` и
`redirectTo` и **ничего про PKCE не отправляет** (`:757-773`). GoTrue нечему
сопоставить код, поэтому он возвращает токены во фрагменте.

Дальше две вещи сложились в баг:

* `supabase_flutter` считает диплинк «своим» только если во flow-типе pkce
  есть `?code=` (`supabase_auth.dart:183-189`), — фрагмент он игнорирует;
* `getSessionFromUrl` при pkce **бросает** `AuthPKCEGrantCodeExchangeError`,
  даже не заглядывая во фрагмент (`gotrue_client.dart:863-871`).

Значит ссылку никто не подобрал, она доехала до Flutter как обычный маршрут,
GoRouter такого адреса не знал — и показал исключение.

### Что сделано

`lib/services/auth_link.dart` — одно место, которое понимает входящую ссылку в
любом виде:

* `params()` читает query и fragment вместе, так что остальному коду всё равно,
  где лежат данные;
* `?code=` → `getSessionFromUrl` (PKCE), тип берётся из события, которое
  поднимает обмен, — в самой ссылке типа нет;
* `#refresh_token=` → `setSession(refreshToken)`, обход того, что
  `getSessionFromUrl` во фрагмент не смотрит; заодно это возвращает свежего
  пользователя с уже новым адресом;
* `error` / `error_description` в любой из половин → отказ с понятным экраном;
* повторная доставка той же ссылки (SDK и Flutter приносят её оба) не
  обменивается дважды, а если верификатор уже потрачен SDK — это считается
  успехом, а не ошибкой.

Роутер: `redirect` ловит любую ссылку-колбэк и уводит по назначению
(`recovery` → `/new-password`, `email_change` → `/settings`, `signup` →
`/splash`, отказ → `/auth-link-failed`). `errorBuilder` больше не печатает ни
адрес, ни исключение — вместо этого экран «Ссылка не открылась» с одной
кнопкой. Проверка `isCallback` — поиск по карте параметров, обычная навигация
на ней ничего не теряет.

После email_change приложение открывает настройки и говорит
«Почта подтверждена: …», а строка «Аккаунт» показывает адрес — она смотрит на
`currentUserProvider`, который обновляется по событию сессии.

### Живая проверка, все три типа

Настоящее установленное приложение, ссылки открывались через Safari — то есть
так же, как их откроет человек из почтового клиента.

| письмо | что в ссылке | куда попало приложение |
|---|---|---|
| `type=signup` | `pkce_75080c70…`, `?code=` | `◀ Safari` → сплэш → онбординг (аккаунт новый, профиля нет) |
| `type=recovery` | `pkce_82d00969…`, `?code=` | `◀ Safari` → **«Новый пароль»** |
| `type=email_change` | токен без `pkce_`, `#access_token=` | `◀ Safari` → **«Настройки»**, в строке «Аккаунт» — `salamat-ec-fed647@mailinator.com`, ниже «Войти в другой аккаунт» и «Сменить пароль» |

Ни одного `Route not found`. Проверено на сервере: оба адреса после перехода —
